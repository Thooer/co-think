# 和 LLM 一起想、一起做

一份在项目里和 LLM 一起想、一起设计、一起做时用的 `AGENTS.md`。它约定怎么提出判断、怎么来回确认、怎么在做的过程中学。

## 适合什么

没有现成答案、要边做边想清楚的事：设计一个系统，理清一个想法，做一件还没成形的东西。规则里写明了范围，一次性的小任务不必套用，套用只会变慢。

## 它改变什么

左边是常见的默认倾向，右边是这份规则要求的。

- 把你的话当指令逐条执行 → 当线索：逐条接住，说清怎么把它们连起来，帮你把模糊的感觉变成可检验的说法，不替你下结论。
- 照你写的做法去做 → 按你的意图做；做法和意图冲突时，按意图做，并指出冲突。
- 每个结论说得一样肯定 → 分清知道、推断和猜，每个结论标出依据。
- 做完一大段再交给你 → 每次停下只留一个需要你判断的问题，没有就不问，说清做到哪、下一步做什么；在会改变方向的地方主动问，带上候选和理由。
- 错了绕过去 → 直接说错在哪、改成什么。

## 为什么这样

「没找到答案」和「还没想到该问这个问题」是两回事。起初我想把这套规则做成一个 skill，讨论一度绕到了怎么搭项目模板。后来才把要求说清：我想在和 LLM 一起设计时就按这套方式来回，不是要它在某个任务里临时走一套流程。这个要求一摆出来，要做的东西也变了：一份 `AGENTS.md`，不是一个 skill。

来回的价值就在这里。LLM 说清它怎么判断、哪里还拿不准，人才能补线索、改问法，再一起拿具体场景检验。如果一个现成概念能换个角度，也用手头的事试一遍。这样做完一件事，带走的不只有结果，还有下次能自己用的问法和判断。

## 怎么用

用 Pi 或其他会读取 `AGENTS.md` 的工具时，把 [AGENTS.md](./AGENTS.md) 放进项目根目录。已有项目规则就合并；分工或流程有冲突，按你在项目里确认的约定写清楚。其他工具按它自己的项目规则加载方式配置。

## 代价和边界

- 自动加载的项目规则会占一部分上下文。
- 这套方式需要你回应、确认、给反馈，不以减少对话轮数为目标。
- 规则来自作者自己的项目实践；这份公开版没有在别人的项目和不同模型上系统验证。

## 文件

- AGENTS.md：给模型读，写成做什么。
- README.md：给人读，讲为什么。
